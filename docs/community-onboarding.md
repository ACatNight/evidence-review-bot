# 社区用户上手路径

本文从第一次访问仓库的维护者出发，区分**已可使用的本地试点路径**与**尚未交付的社区部署体验**。当前项目适合测试仓库联调，不应把合成示例当成真实审查效果。

## 1. 先判断是否值得安装

先运行 `npm ci`，再运行 `npm run demo:report -- github` 或 `npm run demo:report -- gitee`。命令只调用本地报告渲染器，展示覆盖率、候选、未检查范围和未运行项；它不读取仓库代码、不连接数据库、不调用模型，也不向平台发布评论。报告中的仓库、SHA、候选和模型数据都是合成示例。查看真实检测范围和限制，请读 [SEC-001 实现边界](sec-001-implementation.md)。

这一步的退出问题是：维护者是否认可报告的证据、覆盖和限制表达。示例报告不能用于判断准确率、误报率或运行成本。

## 2. 接入一个测试仓库

当前经项目文档覆盖的路径是 Windows 本机部署：[配置与启停](deployment-windows.md)、[GitHub 本地联调](local-development.md)、[Gitee 接入](gitee-setup.md)。用户只配置自己需要的平台；Gitee 仓库不应要求安装 GitHub App，但当前启动脚本和 Worker **仍要求 GitHub App 配置**，这是待拆分的部署限制。PostgreSQL 与可从平台访问的 HTTPS Webhook 地址也仍需准备。

先选择公开或明确获准的测试仓库。AI 默认关闭；如果开启外部 AI，必须逐仓库确认代码可以发送到选定服务。密钥保存在仓库外，不写进配置模板、命令输出或讨论区。平台权限和数据边界见 [安全说明](security.md)。

接入完成至少核验以下状态，不把前一步成功当作后一步成功：

| 阶段 | 可观察证据 | 失败时先检查 |
| --- | --- | --- |
| 本地进程 | API `/healthz` 返回 `ok`，Worker 持续运行 | 数据库、端口、启动日志 |
| 公网入口 | HTTPS `/healthz` 返回 `ok` | 域名、隧道或反向代理 |
| 平台投递 | GitHub Recent Deliveries 或 Gitee WebHook 记录出现成功投递 | URL、事件订阅、签名密钥 |
| 任务执行 | 队列出现对应 PR 且进入终态 | 平台读取权限、快照、Worker 日志 |
| 报告发布 | 对应 SHA 的 Check 或 PR 评论可见 | 平台写权限、PR 状态、发布记录 |

先创建一个小型测试 PR；确认更新 PR 后能再次触发审查。报告中的 `partial`、`error`、`0` 项候选与 `0% 未运行` 有不同含义，不能统称“通过”。

## 3. 长期运行与多仓库管理

试点稳定后，再考虑常驻主机、备份与恢复、监控、密钥轮换和升级。当前 Windows 启动器依赖本机进程；关机后自动审查停止。Gitee 组织仓库还需要确认令牌能读取代码并发布评论。多仓库管理员需要查看每个仓库的授权、最后一次平台投递、任务状态和报告，而不只查看一个进程的健康灯。

## 4. 社区发布前必须补齐

以下是**计划与验收条件**，不是当前功能：

1. **离线样例与兼容性矩阵**：示例命令稳定运行；明确哪些平台、事件、语言、规则和运行时已真实验证。
2. **推荐自托管路径**：提供带版本固定、健康检查、数据卷、升级和回滚说明的 Docker Compose；同时保留已有基础设施接入方式。不能只给一份未验证的 YAML。
3. **按平台最小配置**：只接 Gitee 的用户不必配置 GitHub App；仓库 ID 尽量通过平台 API 获取，内部密钥由安装流程生成。应用权限和平台页面步骤要明确列出。
4. **安装前检查与验证**：一条入口检查数据库、平台授权、Webhook 可达性和真实投递，输出可行动的故障信息。完成状态必须由真实事件与发布结果证明。
5. **独立本地管理界面**：首次设置、仓库和任务状态、脱敏日志、升级与密钥轮换；与公网 Webhook 入口隔离，默认仅本机可访问。macOS 风格仅是视觉参考，Windows/macOS/Linux 用户均应可使用。

优先顺序是离线试读 → 单仓库真实闭环 → 推荐部署路径 → 长期管理界面。这样界面服务于已验证的安装过程，而不是替代尚未解决的部署步骤。
