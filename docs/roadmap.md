# PR 审查机器人：验证路线图

> 状态：待实施路线图。范围以[首版实施基线](mvp.md)为准，任务按验收证据推进，不是交付日期或已完成声明。

## M0：确认试点合同与基线

工作：访谈愿意自托管的团队；确定首个语言与包生态、GitHub 权限范围、数据保留策略、评论预算和密钥处置方式；收集历史 PR、人工审查结论与现有工具输出。为每条候选规则定义检测范围、正例、负例和放弃评论条件。

把 Gitee AI、CodeRabbit、Semgrep、PR-Agent 纳入[竞品对照](competition.md)，选择试点已在用的流程作为效果基线。平台兼容、自托管与多模型不计作已证明优势；按[评估计划](evaluation.md)预先确定有用发现、无用评论、核查时间与维护成本的判定方法。

退出条件：至少找到能提供真实 PR 与复核反馈的试点仓库；形成书面数据处理约定；测量现有扫描器的评论量与有用率作为基线。若首批用户并非 JS/TS/npm 团队，调整语言选择，不强推默认组合。

试点招募与技术实现可并行。以下 M1 可先用公开仓库和合成夹具推进；M0 未完成时不把演示样本当作真实试点结果。

## M1：SEC-001 端到端最小闭环

工作：实现 GitHub Webhook 验证、事件入队、固定 merge-base/base/head 快照、版本化分析去重、diff 定位、密钥候选检测、脱敏证据、Check 摘要和审计记录。按数据模型分别处理事件、分析运行与发布幂等。新提交使旧任务失效；发布前再次核验 base/head SHA。提供关闭规则、抑制、显式重跑及人工反馈入口；行评论先在测试仓库验证，默认关闭。

退出条件：在测试仓库完成安装、授权、PR 更新、重复事件、重跑、快速连续提交和权限失败的真实平台验证；故障能通过 Check 或日志定位；没有原始密钥出现在评论、普通日志和存储证据中。规则正例、负例、回归集通过，历史 PR 静默回放完成初步人工标注。

可靠性门槛：故障注入覆盖 Worker 崩溃、租约过期后旧 Worker 恢复、外部发布已成功但本地未记录、目标分支推进、diff 不完整及零 Finding 的摘要。新 head 创建新 Check，同一问题重跑不刷屏；超时发布进入 uncertain 对账，不盲目重复创建。测试需保留数据库状态与脱敏平台输出作为证据。

可信性门槛：提供实际可操作的证据查看、反馈录入和审计导出入口；确定性回放两次得到一致的规范化结果，输入缺失返回明确原因，回放没有平台写入。先用受保护 CLI/API 满足，不以完整管理后台作为前置条件。

### M1 开发任务与依赖

以下全部为待完成任务，可作为逐个交付的开发单元。A 编号对应实施基线，不表示测试已经存在。

| 任务 | 依赖 | 交付物与完成条件 |
| --- | --- | --- |
| T01 工程与领域契约 | 无 | 锁定运行时/依赖版本；类型检查、构建、测试命令；Snapshot/Finding/Evidence/Coverage 类型不依赖 GitHub SDK |
| T02 PostgreSQL 与任务恢复 | T01 | 迁移、事件去重、snapshot/analysis job、租约 fencing、审计；A01/A02/A07 |

| T04 SEC-001 与证据 | T01/T03 | 比较并选择检测器，锁定版本/格式清单；正反例、脱敏、变化归因与证据来源；A03/A04 |

## M2：小规模真实试点

工作：先静默运行并由人工复核，再有限开启高置信评论；记录每条评论是否准确、是否值得打扰、修复或忽略原因。比较现有工具和人工审查的基线。跟踪每 PR 处理时间、错误、评论数及运行成本。

按仓库/时间划分校准集与留出集，两人独立标注并裁决；同一批 PR 同时观察有用发现是否保留和无用评论是否下降。规则或阈值变更必须生成新版本，复核后才启用。若没有足够增量价值，优先收窄为证据/结果筛选组件，再决定下一阶段投入。

退出条件：按 [产品定义](product.md) 中的样本量与口径报告结果；没有未解决的严重信息泄漏或重复刷屏；高置信评论精确率达到试点双方约定的门槛，且区分自然样本与构造样本。若样本不足或误报高，先收紧规则，不扩展平台与 LLM。

## M3：依赖漏洞与输出质量

工作：按 DEP-001 基线接入一种公告源和受支持的 npm 锁文件格式；只对可确定的版本给出受影响结论，记录公告来源、更新时间、匹配依据、修复版本及误差情况。若试点选择已有 SCA 输出，应先记录 ADR 替换接入路径。完善评论去重、旧评论处理、抑制到期和覆盖范围说明。

退出条件：用真实 npm 锁文件验证直接与传递依赖、版本范围、无修复版本、公告更新、锁文件未改变等情况；对没有精确版本或数据库不可用的情况明确显示“未判断”，不发布确定性漏洞结论。重新测量每 PR 评论量及准确率。

## M4：可选规则和语义实验

ERR-001 作为仓库可选规则，默认关闭；启用后将 AST 能确定的空 `catch` 放入汇总，由试点确认该团队是否视其为需处理的问题。LLM 仅做 shadow 实验：限定问题类型与上下文预算，比较人工标注结果、延迟、每 PR 成本和隐私影响；模型候选不自动发布。只有在某类语义问题上证明足够的增量价值后，才讨论受控上线门槛。

## M5：平台扩展和开源发布准备

在真实 Gitee 仓库确认可用授权模式和 Webhook 认证机制，再验证 diff 获取、行评论定位、状态或替代输出、权限及 API 限额。平台接口按能力声明；缺失 Check 等能力时使用明确的降级输出，不假设平台事件标准化后差异消失。

M1 已交付基础部署与运维说明；此阶段针对新增平台更新权限、配置、数据处理和故障排查内容。公开发布提供可运行示例和标明已验证平台/语言/规则的兼容性矩阵；未验证的能力不列为支持。

每个里程碑保留：范围变更、样本来源与标注口径、规则版本、解析器版本、公告快照或查询记录、评估指标及失败案例。按实施基线采用 TypeScript/Fastify/PostgreSQL，T01 锁定准确版本；遇到实际部署阻碍时更新 ADR。已决定的默认方案不在每个任务重新讨论，未验证能力继续标注待验证。
