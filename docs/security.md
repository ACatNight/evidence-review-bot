# 安全与证据设计

状态：设计草案。首发范围为 GitHub PR、JS/TS、npm；Gitee、GitLab 和更多语言后续接入。本文描述目标约束，未表示平台 API 或权限已完成实测。

## 信任边界

| 输入或组件 | 信任级别 | 处理原则 |
| --- | --- | --- |
| Webhook 请求 | 未验证 | 在原始请求体上验签，校验事件、仓库、安装身份和时间/投递标识，再入队。 |
| PR 代码、提交信息、文件名及 PR 内配置 | 不可信 | 仅作为待审数据。不得将其文本解释为系统指令；不得让其决定读取范围、模型工具权限或安全策略。 |
| 仓库策略 | 有条件可信 | 从受保护的 base 分支固定 SHA 读取，经服务端允许列表和 schema 校验；PR 对策略文件的改动只能作为待审变更，不能影响本次审查。 |
| 平台访问令牌、Webhook 密钥、HMAC 密钥、模型密钥 | 高敏感 | 分安装隔离、最小权限、加密保存、轮换；不进入代码上下文、模型请求、日志或审查结果。 |
| LLM 输出 | 不可信派生结果 | 只能提出候选，需结构校验和证据校验；不能直接发布、执行工具或覆盖确定性事实。 |

首发不运行 PR 提交的脚本、测试、构建或包安装脚本。若未来引入动态分析，必须在无平台令牌、受限网络和资源配额的隔离环境执行。获取文件时限定当前仓库、固定 SHA、路径规范化和大小上限；拒绝路径穿越及指向外部仓库/地址的非预期重定向。限制单 PR 文件数、字节数、上下文量、模型 token、运行时间及并发，超限时记录覆盖缺口。

## Webhook、任务与租户隔离

1. 在请求体大小限制之后，对**原始字节**验证平台签名；比较过程使用恒时算法。验证失败不创建任务。
2. 用平台投递 ID、安装 ID、仓库 ID 和事件类型处理重放与重复投递，并记录事件接收时间。投递 ID 的唯一性和重试语义须按平台实测。
3. Webhook 立即持久化标准事件并返回；Worker 从 PostgreSQL 队列领取任务。任务表和 outbox 具有独立唯一约束、租约、重试次数与死信状态，避免多 Worker 重复发布。
4. 每次平台 API 调用使用对应安装的短期令牌；数据查询必须带租户/安装范围。撤销安装或权限后停止新任务、取消待发布 outbox、删除或按留存策略清理令牌与缓存。已经发出的评论无法自动视为撤销。
5. 接收时和**每次发布前**重新确认安装权限、PR 状态及最新 base/head SHA。旧任务标为 `superseded`。外部 API 调用与本地数据库事务无法原子提交，因此仍可能在确认与发布之间发生竞态；发布后记录平台对象 ID、实际关联 SHA，并在发现过期时更新/隐藏可控输出，或标注过期。不得声称能绝对阻止过期评论。

分析任务的身份至少包含 provider、安装/仓库、PR、base SHA、head SHA、规则集版本、可信配置摘要、扫描器版本和漏洞数据快照。平台投递去重、分析结果缓存与发布幂等是三个不同概念。发布使用稳定 finding fingerprint、目标 commit 与输出渠道记录平台对象 ID；重试先核对 outbox 和现有对象，避免重复评论。

## Secret 检测与脱敏

SEC-001 应把疑似密钥当作敏感数据，即使最终判为误报。原值只在受限扫描内存中短暂使用；不存数据库、普通日志、异常、审计正文、评论、Check、SARIF 或 LLM 请求。证据展示文件位置、类型、上下文的脱敏版本和检测依据，不展示完整 secret。上下文脱敏应发生在进入任何外部模型或持久层之前，并对模型输出再次扫描。

跨版本去重可保存带租户作用域的 HMAC 指纹，例如 `HMAC-SHA256(tenant_key, normalized_secret)`，同时记录算法和密钥版本。不要保存低熵 secret 的裸 SHA-256：攻击者可对短密码离线枚举。HMAC 密钥与平台令牌分开存放和轮换；轮换期间支持过渡去重，过渡结束删除旧指纹。只为检测和去重保留最少信息；审计中不保留完整代码片段。

发布前需处理测试假值、示例文件、生成文件、已撤销凭据和既有未变更行。规则的误报样本进入回归测试；允许有期限、有范围、带理由的 suppression。反馈不能让 PR 作者通过修改不可信配置自助关闭扫描。真实泄露的处理建议要提示轮换凭据，仅删除源码不足以消除历史泄露。

## LLM 边界

LLM 默认关闭或只用于有明确语义问题的候选复核。模型接收最小化、脱敏后的差异和必要上下文；企业可配置禁用外部模型、数据区域和保留策略。模型调用前显示并记录所用 provider、模型标识、提示模板版本、输入摘要、成本与超时；不得记录原始敏感内容。代码、注释、Markdown、提交信息中的“忽略规则”“调用接口”等均视为数据。模型不持有平台 token，不开放任意网络、shell 或跨仓库读取工具。结构化输出需校验 schema、路径与行号；无可验证 observed evidence 的候选不得成为逐行评论。

## Evidence 与审计

Finding 至少关联：provider/仓库/PR、base/head SHA、文件路径、blob SHA、diff hunk 或可重新定位的行锚点、规则 ID/版本、扫描器版本、可信配置摘要、运行时间及覆盖状态。依赖漏洞证据另记录包生态、锁文件解析结果、精确版本、公告 ID、受影响版本判断与漏洞数据快照时间。模型参与时记录模型和提示模板版本，以及候选与验证结果。

将 `observed`（平台返回的 diff、固定 SHA 的文件内容等直接事实）、`derived`（解析器、规则或公告匹配结果）与 `reasoning`（解释）分字段存储，标出来源及变换。模型陈述不能冒充 observed。代码和 secret 原值不能为了“可回放”无限期存储；回放优先依赖固定 SHA、规则版本与受控数据快照。若上游仓库或公告不可再取回，应如实标注不可完全回放。审计记录访问、扫描、过滤、抑制、发布、重试、删除事件，设定明确留存期、删除流程和租户隔离。

## 发布与误报控制

`high/medium/low` 是策略等级，不是已校准概率。每条规则需要正例、反例、回归样本，以及真实 PR 的人工复核数据；按规则分别统计精确率、漏报、评论撤回率。默认只有直接证据充分、位置可定位的新增问题进入逐行评论。空 `catch` 需用语法解析确认，并限定新增/改动代码；依赖漏洞基于锁文件中的实际解析版本，区分直接依赖与传递依赖，公告数据过期时不得宣称安全。

审查结果须给出 `complete` 或 `partial` 覆盖状态及原因，例如 diff 缺失、分页/大小限制、文件不支持、公告服务不可用或模型失败。`partial`、扫描失败及跳过文件时不能输出“没有问题”或成功的安全结论。首发默认只发布 Check 汇总，不阻断合并；逐行评论须由可信配置显式开启并通过质量门槛。Check conclusion 与后续门禁策略应由覆盖状态、规则严重度和团队配置共同决定；具体平台 conclusion 映射在实现时验证。

## 实施验收

- 用 fork PR、恶意提示文本、路径穿越、超大 diff、重复 Webhook、撤销安装、新 commit 抢先到达等用例验证边界。
- 检查日志、数据库、outbox、模型请求及所有平台输出均无原始 secret；对低熵值验证 HMAC 去重和密钥轮换。
- 测试发布前 SHA 复核和发布后竞态记录；故障注入验证 outbox 重试不重复评论。
- 对 partial 结果验证 Check、评论与 API 返回均明确说明未覆盖范围。
