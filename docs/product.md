# PR 审查机器人：产品边界与试点定义

> 状态：产品建议稿，供试点讨论。本文定义拟验证的产品，不代表功能已经实现，也不代表用户已确认技术栈。

## 1. 产品判断

产品定位为开放、平台无关的 PR Review Engine：以确定性检查和可验证证据支持审查决策，在 PR 中报告少量、可核查的问题，并让维护者知道结论来自哪段代码、哪条规则和哪次分析。首批用户是愿意自托管、已使用审查或扫描工具、仍受误报与结果追溯困难影响的中小研发团队。价值应通过真实 PR 中的有用发现和节省的人工核查时间验证，不能只用“发现了多少问题”衡量。

建议以 GitHub 首发，选择 JS/TS + npm 作为**待试点验证的默认组合**。它便于获得公开样本和验证锁文件解析，但最终语言与包生态由试点团队决定。Gitee、其他生态和 LLM 语义审查均不应成为第一轮上线条件。优先提供自托管部署，避免在早期承担托管服务的代码隐私、可用性和推理成本。

当前实施范围以[首版实施基线](mvp.md)为准：M1 只交付 SEC-001 和可信审查流程，npm 漏洞分析属于 M3。试点语言可调整，但技术闭环可先按当前基线开发。

Gitee AI / AI 队友、CodeRabbit、Semgrep 和 PR-Agent 与本方案存在直接或部分重叠。平台接入、自托管、多模型/BYOK、团队规范与 RAG 均不能单独视为独有能力；也不能根据介绍未提及就断言竞品没有证据链或审计。见[竞品与差异化](competition.md)的官方来源与边界。

当前待验证的价值主张是：在保留有用发现的同时减少无用评论，并让每条发布或抑制决策能够核查和反馈。证据链证明来源和处理过程可检查，并不自动证明缺陷成立；确定性也不保证规则无误。比较方法和回放边界见[回放、审计与评估](evaluation.md)。GitHub 为首个参考适配器，Gitee 保留兼容方向；若试点必须使用 Gitee，可先验证其 API 后调整平台顺序。

## 2. 首批用户与使用流程

目标试点：5–10 个愿意提供人工复核反馈的仓库，包含不同 PR 大小、代码质量和依赖更新方式；优先选有现成 CI 与审查流程的团队。公开仓库便于起步，私有仓库需要额外确认权限、数据保留和第三方服务策略。

预期流程：管理员安装并限定 GitHub App 仓库权限 → 配置规则 → PR 更新触发审查 → Check 展示状态、范围与证据摘要 → 授权维护者录入问题判断与独立的风险处置 → 下次运行据明确配置或抑制记录调整输出。行评论是通过质量门槛后的可选输出。反馈标签以数据模型为准，用于人工改进规则和评估，不自动训练模型，也不自动改变规则阈值。

默认发布策略：只更新 Check，逐行评论需要可信配置显式开启并通过质量门槛；结果无法定位到当前 diff 时放入摘要；对新 commit 的旧结果明确标记过期；同一问题在重跑中不重复刷屏。规则级关闭、仓库级配置和有理由、有期限的抑制需要有可审计记录。

## 3. 范围与阶段

| 阶段 | 纳入 | 暂不纳入 |
| --- | --- | --- |
| 第一闭环 | GitHub App/Webhook、PR diff 与当前 SHA 校验、SEC-001 高精度密钥候选、证据脱敏、Check 摘要、受控行评论、幂等与反馈记录 | Gitee、自动修复、团队知识学习、默认 LLM 审查 |
| 第二步 | DEP-001：对 npm 锁文件中的**精确版本**匹配已知漏洞，并解释受影响范围、来源与修复版本；明确数据源和更新时间 | 对模糊版本声明猜测已安装版本；自建通用 SCA 平台 |
| 可选规则 | ERR-001：仅检测 AST 能确认的空 `catch`，默认关闭，由仓库自行启用 | 把所有空 `catch` 当作必然 bug；对复杂异常路径直接判错 |
| 后续实验 | LLM 在 shadow 模式分析语义问题，只记录候选供人工评估，不自动评论 | 未验证准确率就发布模型结论或承诺可重复生成相同文本 |
| 后续平台 | Gitee 适配，先验证授权、Webhook、diff 定位、评论和状态能力，再决定输出降级 | 假设平台能力完全相同 |

SEC-001 的首批触发条件应保守：只分析新增或修改代码，使用可解释的模式、上下文与排除规则；明显的测试占位符、示例和已知假值进入负例库。命中后不要把原始密钥写入评论、普通日志、审计记录或发给 LLM。建议显示文件、行、已脱敏片段、规则版本和轮换建议；若密钥可能真实有效，提示撤销或轮换，而非仅建议移到环境变量。

DEP-001 的 M3 基线为受支持锁文件精确版本与一种可靠公告源的最小匹配，复用生态版本处理库，承担包名规范化、传递依赖、数据时效和异常处理。导入既有 SCA 结果属于替代接入路径，若试点更适合此方案，通过 ADR 替换，不同时开发两套。两种路径都需保留原始工具或公告来源，不声称已构建通用 SCA。

## 4. 证据和可追溯性的定义

每条 Finding 至少包含规则 ID/版本、仓库与 PR、base/head SHA、当前文件与行、检测方法、脱敏后的观察事实、派生事实及其来源、推理说明、建议、去重键和分析时间。证据分三层：

1. **观察事实**：在指定提交和文件中能重新读取的内容，敏感值只保留脱敏形式与必要指纹。
2. **派生事实**：AST、锁文件、公告或其他工具算出的结论，必须带工具版本、输入摘要和公告标识。
3. **解释**：为何这些事实构成该规则的问题；不能把模型推断伪装成代码事实。

“证据可追溯”意味着能找到原始输入及分析版本，**不等于**任何时候都能重新获取外部公告或 LLM 的逐字输出。“可复现”需固定代码 SHA、规则版本、解析器版本和公告快照或查询结果。后续 LLM shadow 实验还需记录模型标识、提示词版本、上下文摘要与响应；即便这些相同，也不承诺重新调用会得到逐字一致的回复。

信心等级不能只由模型自报。评论门槛由规则的可观测条件、证据完整性、定位准确性和试点测得的误报率决定。证据不足、基础设施失败或 head SHA 已变化时，不应生成当前有效的问题评论。

## 5. 试点验收与学习

先对历史 PR 做静默回放，再在真实 GitHub 安装环境做小范围运行。建议覆盖至少 5 个仓库、100 个 PR，并收集足够的候选问题供两名人工审查者独立标注；若正例稀少，应补充带明确标签的测试/回归样本，同时分别报告自然样本和构造样本。样本量是试点计划值，不是已取得的证据。

按规则报告精确率 TP/(TP+FP)、错误发现占比 FP/(TP+FP)、召回率 TP/(TP+FN)，其中 TP/FP 限定在同一待评估候选或发布集合，FN 来自完整标注的检测范围。传统假阳性率 FP/(FP+TN) 只有定义并标注负例总体时才报告，不能与错误发现占比混用。另记录每 PR 评论数、反馈响应率、评论采纳率、完成时延及部署/运行成本。召回率只对定义了可检测范围的人工标注集有意义；不能从“没有用户投诉”推断召回率。指标附样本量、标注分歧与区间估计，不作产品承诺。建议公开行评论以每条规则至少 100 条已裁决候选、精确率点估计达到 95% 为初始讨论门槛，并分别报告自然样本与构造样本；这仍不是总体准确率保证。没有严重信息泄漏是独立硬性条件。样本不足时继续静默或汇总试点。

人工反馈应区分误报、问题真实但不值得评论、问题有效、已接受风险。它可形成回归用例或经审核的仓库抑制规则；不得自动改写检测逻辑或训练数据。每条规则变更至少有正例、负例、回归样本，并在试点数据上重新评估评论噪声。

## 6. 主要待验证问题

- GitHub App 所需最小权限、Webhook 重投和行评论定位在真实 PR 中的行为。
- 密钥检测的误报与脱敏：尤其测试凭据、模板变量、生成代码和复制到评论中的信息。
- 试点仓库的语言/包生态是否支持 JS/TS + npm 作为第一组合。
- 公告源的许可、速率限制、更新时间和版本范围匹配质量。
- 自托管安装难度、升级与故障排查成本是否适合目标团队。
- 如果用户已启用 CodeQL、Semgrep 或依赖扫描器，机器人补充了什么价值。
