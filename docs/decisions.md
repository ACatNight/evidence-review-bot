# 架构决策记录

日期：2026-10-01。状态：讨论后的推荐设计，尚未实现。文中“采用”表示当前文档基线；实现阶段需通过验证后确认，不代表用户已逐项批准技术选型。

## ADR-001：GitHub 首发，平台差异留在适配层

首版打通 GitHub App。Gitee、GitLab 保留后续接入方向，不为未知平台能力提前实现空接口。

核心接收统一快照和证据，发布层查询平台能力。授权、Check、行评论、权限、限流和事件语义不能被一个统一接口抹平。

代价：首版无法服务只使用 Gitee 的团队。若首个真实试点明确依赖 Gitee，应先完成其 API 能力验证，再调整接入顺序。

## ADR-002：模块化单体，API 与 Worker 分进程

推荐 TypeScript、Node.js 实施时仍受支持的 LTS、Fastify、PostgreSQL。实现开始时锁定准确版本与依赖锁文件，并验证部署环境。推荐此栈的原因是平台 JSON 接口接入方便，且可复用 JS/TS 解析工具；分析语言和服务实现语言并非必须一致。

API 和 Worker 共享领域模块与数据库 schema，可以分别扩容。初期由 PostgreSQL 持久化任务、租约与 outbox，避免数据库和独立消息队列之间额外的双写一致性问题。数据库队列仍需实现重试、租约续期、死信与清理；并非免费获得可靠性。

不提前采用微服务。出现数据库任务争用、队列吞吐瓶颈或独立服务隔离需求时，以指标和故障记录决定是否拆分队列或服务。

## ADR-003：先做可靠审查闭环，再验证语义价值

首条规则选 SEC-001 的高精度子集；DEP-001 在精确锁定版本和公告来源可追溯后接入；ERR-001 作为可配置团队规范，默认关闭。

LLM 的首个实验采用静默模式，例如评估错误处理是否改变调用方可见行为；必须包含调用点等证据，不能因为模型自报高置信度就发布评论。

代价：最早原型的 AI 能力有限。收益是否成立由试点中有效评论、误报、漏报与节省审查时间共同衡量。

## ADR-004：三类标识分别承担不同责任

- 事件键去重平台重复投递。
- 分析键绑定快照、规则、可信配置、分析器与外部数据版本；允许配置变更和显式重跑。
- 发布键绑定输出目标及问题身份，用于对账和避免重复评论。

问题跨提交的稳定身份单独管理，避免把代码行号当作唯一身份。数据库唯一约束与租约负责内部幂等；外部 API 超时可能已完成写入，必须先查询对账再重试。不能承诺跨数据库和平台的 exactly-once。

## ADR-005：证据可追溯与重跑结果一致分别描述

证据必须能定位到固定 commit/blob、规则和分析来源。确定性重跑还需要相同解析器、配置与漏洞公告快照；没有保留相同输入时只能重新分析，不能声称精确复现。

LLM 保留脱敏请求引用、模型标识、提示模板版本、参数及结果。相同设置不保证模型返回相同结果。Secret 原文不为复现目的长期保存；重跑依赖仍有权限访问相应代码快照。

## ADR-006：Check 汇总优先，发布策略独立于严重程度

默认不以审查结果阻断合并。逐行评论需要用户配置开启、规则通过质量门槛、证据有效、锚点可定位和运行仍有效。高严重程度不自动代表高准确率。

后续若启用 required check，单独定义失败策略及部分覆盖处理，不能把工具失败显示成代码通过。平台结论映射见平台文档。

## ADR-007：自托管与显式模型数据流

首版部署目标为单组织自托管，同时按 installation/repository 隔离访问。关闭 AI 时不向模型服务发送源码；开启 AI 需配置允许的仓库、模型目标和可传输的数据范围。

未来支持国内或内网模型通过适配器完成；不同模型的结构化输出、上下文、成本和效果分别验证，不假定兼容接口等于能力一致。

## ADR-008：平台兼容与竞争优势分别验证

2026-10-01 依据官方资料重新审视定位：Gitee AI 已提供原生 PR 审查与团队手册配置；CodeRabbit 的公开架构包含静态分析工具，其企业方案提供自托管与自选模型；Semgrep、PR-Agent 也与部分候选能力重叠。来源见[竞品与差异化](competition.md)。

采用“开放、平台无关的 PR Review Engine，以确定性检查和可验证证据支持审查决策”的定位。平台支持、BYOK、多模型、自托管和团队知识分别作为兼容、部署或扩展能力，不据此宣布竞争壁垒。团队文档不能未经审核直接变成可执行规则，反馈也不能自动训练或改变阈值。

首个价值假设是保持有用发现并减少无用评论与人工核查时间，必须与同一批 PR 上的现有工具流程比较。回放、审计、证据完整性和标注数据形成可测试契约；在完成试点前均是设计目标。Gitee 保留，GitHub 首发和现有规则范围不因定位调整自动扩大。

## ADR-009：统一首版边界与可执行交付顺序

优化后以[首版实施基线](mvp.md)统一范围。M1 只交付 SEC-001、Check、基础反馈/抑制、证据查看、审计导出和无副作用回放；M3 再加入 npm 公告匹配。按路线图 T01–T07 推进，实际试点招募不阻挡公开/合成夹具上的技术开发。

任务状态、运行状态、覆盖状态和发布状态分别描述；snapshot 任务先于 review_run。同 SHA 的新运行通过 desired_run_id 与 publish_generation 保护汇总，replay 不进入发布链。反馈真假判断与风险处置分字段，审计保存可读脱敏元数据而非只有摘要。以上约束的测试编号集中为 A01–A12。

默认方案用于指导实现，不等于 API、检测精度或部署已验证。改变范围应同时更新基线、受影响契约和 ADR，不要求每个开发任务重复确认同一选择。

## 进入实现前的验证事项

| 问题 | 推荐默认 | 验证方式 |
| --- | --- | --- |
| 首个用户与平台 | GitHub 小团队、自托管 | 真实试点确认，记录平台与语言 |
| 首个生态 | JS/TS + npm | 收集代表性 PR 与锁文件版本 |
| Secret 工具 | 优先评估成熟检测器的受控集成 | 比较精度、脱敏、许可证与进程隔离；再确定是否自写小型规则 |
| 公告来源 | 通过 AdvisorySource 接口接入一种来源 | 验证版本匹配、查询隐私、快照可留存性与使用条款 |
| Gitee 接入 | 首版后验证 | 用测试仓库验证授权、事件、diff、评论和状态能力 |
| 资源与留存预算 | 配置化、有明确上限 | 用代表性 PR 测量后确定值 |
| 对外发布阈值 | 默认为静默与汇总 | 达成路线文档的样本与质量门槛后调整 |

决策变更需记录原因、受影响文档和迁移方式。本文不替代实现代码、API 集成证据或压测报告。
